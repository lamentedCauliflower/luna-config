# Use sops-nix With SSH-Derived Age Keys For Secrets

We will manage all secrets with sops-nix: a single `secrets/secrets.yaml` encrypted to four age recipients — the three hosts' existing SSH ed25519 host keys (via ssh-to-age) and Isaac's personal ed25519 key (the **Admin Key**, the only key a human edits with). No dedicated age keys are generated or provisioned; a host that can SSH is a host that can decrypt. Secrets materialise at activation under `/run/secrets`; docker compose stacks consume them through sops-rendered env-files (`env_file:`), home-manager consumers read root-declared secrets owned by `isaac`, and the syncthing GUI password is the one exception — committed as a bcrypt hash since the NixOS module offers no file indirection.

One wrinkle discovered during migration: neither sops nor ssh-to-age can read passphrase-protected SSH keys, so the Admin Key's age identity was derived once from a temporarily-decrypted copy and stored **unencrypted** in `~/.config/sops/age/keys.txt` (mode 600). That file decrypts every secret but cannot SSH anywhere; it is guarded by filesystem permissions only — an accepted trade-off over YubiKey/agenix-rekey ceremony.

Considered options were agenix (no templating, weaker home-manager story), agenix-rekey (extra master-key ceremony), deploy-time secret push via deploy-rs/colmena (adds a deploy tool and makes the admin machine a single point of loss), and dedicated per-host age keys (manual provisioning per host and per reinstall). We deliberately keep the existing secret values rather than rotating: their only exposure was the LAN-only gitea history and the hosts' own nix stores, and the git history is being destroyed (local `.git` and the gitea repo deleted, repo re-initialised) before the repo is ever published publicly on GitHub. A future reader should not "fix" the missing rotation — it was traded away against re-provisioning every service credential, on the condition that the plaintext history dies first.
