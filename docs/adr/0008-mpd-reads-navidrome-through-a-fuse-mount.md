# MPD Reads Navidrome Through A FUSE Mount, Not A Subsonic-Aware Daemon

Music on the desktops used to come off the NFS export: `services.mpd.musicDirectory` was `/mnt/media/Music`, the same files lunaServer hands to Navidrome. That works at the desk and nowhere else — the NFS mount is `nofail`, so a laptop away from the LAN simply has an empty library, and the two halves of the setup (mpd's tag cache, Navidrome's play counts and stars) drift apart because they index the same files twice. The library should have one reader, and it should be reachable over tailscale.

mpd has no Subsonic backend and is never going to grow one. The three ways out are a different daemon, a bridge, or a filesystem.

**A different daemon — mopidy.** `mopidy-subidy` speaks Subsonic and `mopidy-mpd` re-exports the MPD protocol, all three packaged in nixpkgs with a home-manager module. Rejected: mopidy-mpd implements the protocol as it stood around mpd 0.19, and rmpc — the client actually used here — wants a modern one. Trading the client for the backend is the wrong way round. mopidy-subidy's upstream is also explicitly looking for a maintainer.

**A bridge — upmpdcli.** The [Navidrome discussion](https://github.com/navidrome/navidrome/discussions/2324) that started this recommends GioF71's Subsonic plugin for upmpdcli, which is a genuinely good fit for its own use case: it publishes a UPnP/DLNA renderer that phones and Kodi can push to, with mpd buried inside as the audio engine. That is the part that disqualifies it here. Control is a UPnP control point (BubbleUPnP, upplay), not rmpc, so "mpd on the clients" would be true only in the sense that some mpd process exists. It is also absent from nixpkgs, so it would arrive as a docker container on a desktop with the pipewire socket passed in, or as a derivation for upmpdcli plus libupnpp plus a plugin that lives outside both.

**A filesystem — httpdirfs.** `httpdirfs` mounts an Airsonic/Subsonic server as an ordinary directory tree (`--sonic-username`/`--sonic-password` select that mode, `--sonic-id3` gives an Artist/Album/Song layout instead of the server's raw index). mpd then indexes it like any other `music_directory`. Nothing about mpd changes, so rmpc, waybar's mpd module and `mpc` all keep working with no protocol caveats, and the only new moving part is one user unit. Navidrome is named in its compatibility list. This is what `homeModules.mpd` now does: `navidrome-mount.service` mounts `http://navidrome.luna.local` at `~/mnt/navidrome`, and that path is the music directory.

Four details in that module are load-bearing:

1. **`--cache` is mandatory, not a tuning knob.** Every tag mpd reads during an update is an HTTP range request against Navidrome. Without the permanent segment cache the first scan is not slow but unusable, which is the failure mode people report when they try this and conclude FUSE is the wrong answer. The cache lands in `${XDG_CACHE_HOME}/httpdirfs`; `httpdirfs --cache-clear` is the escape hatch, which is why the package is in `home.packages` and not merely referenced by the unit.

2. **Credentials come from `--config=`, never argv.** `/proc/<pid>/cmdline` is world-readable, so `--sonic-password` on the command line publishes the Navidrome password to every local process. The file is a sops template (`httpdirfs-navidrome.conf`, declared system-side in `isaacHomeManager` like every other home-manager secret) holding one option per line — httpdirfs appends the file to its own argument list, see `parse_config_file` in its `src/main.c`. The two-word `--config PATH` spelling is load-bearing and was got wrong first time round: httpdirfs 1.2.10 finds the config path by scanning argv for a plain `strcmp` match on `--config`, so `--config=PATH` leaves the path unread, falls back to `$XDG_CONFIG_HOME/httpdirfs/config`, finds nothing there, and carries on with no credentials. That is not an error — it is a clean mount of an empty tree, which mpd reads as the library having been deleted. The `=` form exists only on git master. Reading the upstream source is not optional here, but read the tag that is packaged, not the default branch.

3. **`ExecStartPost` waits for the mountpoint.** httpdirfs does not implement sd_notify, and the FUSE tree appears some milliseconds after the process does. `Before = [ "mpd.service" ]` orders the login-time start of the two, but only the wait loop stops an mpd that wins the race from indexing an empty directory and writing that to the tag cache.

4. **`auto_update "no"`.** inotify does not cross a FUSE mount that has nothing to report, and the default would have mpd re-walking the whole remote tree for no signal. Updating is manual — `mpc update`, or `u` in rmpc — after Navidrome's own hourly scan has picked new files up. The cost is that new albums are two manual steps behind the filesystem; the alternative is a periodic scan of a network filesystem, which is exactly what the cache exists to avoid.

Two things this deliberately does not solve. Play counts and stars still only move when something calls Navidrome's `/rest/scrobble`; streaming a file through `/rest/stream` does not, so mpd playback is invisible to Navidrome's statistics. The discussion above pairs upmpdcli with a `mpd-subsonic-scrobbler` sidecar for exactly this, and that is the shape any fix here would take too. And `/mnt/media` stays mounted — the emulators and game modules read it — it just is not where music comes from any more.
