# Windows-Game Tiles Force Proton Via A Declarative CompatToolMapping Entry

A Non-Steam Shortcut whose exe is a Windows binary (first case: Voices of the Void) declares `compatTool` on its shortcut (e.g. `"proton_experimental"`). The steam-shortcuts writer — in the same run-before-Steam boot oneshot that merges shortcuts.vdf — upserts a matching `CompatToolMapping` entry into the Steam root's config.vdf, keyed by the shortcut's appid (`crc32(Exe + AppName)`). Steam then launches the tile through Proton exactly as if the tool had been picked in the game's Properties. Tiles without `compatTool` are untouched.

Two constraints follow from the appid keying:

1. **The Exe path must be hash-free and stable.** The appid keys not just the mapping but the game's compatdata prefix (`steamapps/compatdata/<appid>/pfx`) — where its saves live. A store-path Exe would change appid on every package bump and orphan the prefix. Windows-game packages therefore install their tree under `$out/share/games/<name>/` and the module exposes it at the fixed profile path `/run/current-system/sw/share/games/<name>/` via `environment.pathsToLink`. Corollary: renaming a tile (its AppName) also rotates the appid and orphans the prefix.
2. **The compat tool itself is Steam-managed, not shipped.** Stock `proton_experimental` was chosen over declaratively shipping Proton-GE (`programs.steam.extraCompatPackages`): nothing to pin or babysit, at the cost that a host which never installed Proton Experimental prompts for its download on the tile's first launch. Revisit if a game needs GE-specific fixes.

A third constraint surfaced on first deploy:

3. **The container does not see `/run/current-system`.** Proton runs inside the Steam Linux Runtime container (pressure-vessel), which shares `/nix` into the container but not `/run/current-system` — the profile path from constraint 1 resolves on the host and is dead inside the container (observed failure mode: wine bootstraps the prefix, every process exits within ~6 seconds, the game never writes its AppData dir). Each Proton Tile therefore sets `launchOptions = "PRESSURE_VESSEL_FILESYSTEMS_RO=/run/current-system %command%"`, the documented steam-runtime knob for sharing extra host paths. Verified inside the SLR container on cleoDesktop: without the variable the exe path does not exist, with it it resolves. Fallback if Valve ever drops the knob: anchor the Exe on a `$HOME` symlink pointing into the store (`$HOME` is always shared; also verified working) — at the cost of rotating the appid once.

The rejected alternative for running Windows games was umu-launcher + Proton-GE outside Steam (a wrapper-script tile, no config.vdf writes). It avoids touching Steam-owned mutable state but hand-rolls the Proton session Steam already provides, and was turned down in review. config.vdf is rewritten from memory when Steam exits — same as shortcuts.vdf — so the write is only safe from the boot-time oneshot (docs/adr/0003's mechanism), never while Steam runs. If Steam has never initialised a root (no config.vdf), the writer skips it rather than inventing one; the mapping lands on the first boot after Steam has run.
