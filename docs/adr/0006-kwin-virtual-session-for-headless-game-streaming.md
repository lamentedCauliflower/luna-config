# Game Streaming Runs A Headless KWin Session, Not GNOME

cleoDesktop streams games to the Steam Deck over Moonlight. The requirement was a desktop session that games open into, invisible on every physical monitor, running from boot with nobody logged in, and incapable of interrupting whoever is using Hyprland at the desk. GNOME was the obvious session to reach for — `nixosModules.gnome` already exists for mewoSteamdeck's Desktop Mode — and it is the one option that cannot work.

Sunshine's Linux capture backends are `nvfbc`, `wlr` (wlr-screencopy), `kms`, `kwin` (KDE screencasting) and `x11`. There is no xdg-desktop-portal ScreenCast path in mainline. Mutter speaks neither wlr-screencopy nor KDE screencasting, and a headless Mutter presents no KMS output for `kms` to grab, so a headless GNOME Wayland session is not capturable by any backend Sunshine has. The remaining GNOME route is Xorg — a dummy X screen or a forced NVIDIA `ConnectedMonitor` with a fake EDID — captured through `x11`, which upstream describes as the slowest and most CPU intensive method, and which puts a second X server on the same GPU competing with Hyprland for DRM master. Plasma was chosen because `kwin` capture is first-class, and because `kwin_wayland --virtual` renders to a virtual framebuffer that touches no DRM device, no VT and no connector at all. Invisibility is a property of the backend rather than something enforced by configuration. wlroots headless (sway or labwc, captured via `wlr`) would have worked equally well on the capture axis and was rejected only because a full desktop was wanted over the stream; if Plasma's daemons ever prove too seat-dependent, that is the fallback and it is a small change.

The session is a dedicated `streamer` user rather than isaac. Steam is single-instance per user: a Steam client running in the stream session would capture any `steam` launched from the Hyprland desk and map its windows into the wrong session, which is exactly the interruption the feature is forbidden to cause. The cost is a second Steam library on local disk and a second interactive Steam login, done once over the stream itself. Sharing one library between two Unix users was rejected — `steamapps` locking and per-user `compatdata` prefixes make it a permissions problem with no upside, and the existing Proton Tile saves (Voices of the Void) live in isaac's prefix and would not follow anyway. `steamShortcuts` is hardcoded to `User = ${username}` and reaches into isaac's home-manager for librewolf's wrapped package, so the streamer session deliberately gets no Non-Steam Shortcuts; generalising that module is a separate job with no current payoff.

Three guards keep the session off the desk, and each exists because a NixOS default or a global unit would otherwise leak:

1. **`services.displayManager.defaultSession = "hyprland"`.** `plasma6` sets `defaultSession = mkDefault "plasma"` and nothing else in this repo defines the option, so merely enabling Plasma would move the ly login default off Hyprland. This is the single most likely way the feature could have broken its own requirement, and it happens at eval time with no error.

2. **A `$USER` dispatch on `plasma-kwin_wayland.service`.** `systemd.user` units are global, so a plain `ExecStart` override adding `--virtual` would put *every* user's KWin on a virtual framebuffer. The unit instead runs a script that branches on the running user: streamer gets the headless framebuffer, anyone else gets stock. `ConditionUser=` was rejected here specifically — a false condition skips the unit entirely, which is Plasma with no compositor rather than Plasma unmodified. The override is possible at all because `kwin_wayland_wrapper` forwards its own argv verbatim to `kwin_wayland` (`src/helpers/wayland_wrapper/kwin_wrapper.cpp`).

3. **`ConditionUser=streamer` on `sunshine.service`.** The nixpkgs module declares Sunshine as a user service wanted by `graphical-session.target`, and a Hyprland login reaches that target — verified live on this host. Without the condition, logging in at the desk would start a second Sunshine capturing the real desktop and binding the ports. Here skipping the unit is precisely the desired outcome, so the condition is the right tool.

KWin gates the privileged `zkde_screencast_unstable_v1` interface by taking the connecting client's executable path — `/proc/<pid>/exe`, via `executablePathFromPid()` — and searching installed desktop files for one whose `Exec` resolves to the same path, then reading `X-KDE-Wayland-Interfaces` from it (`src/utils/serviceutils.h`, `src/wayland_server.cpp`). Sunshine ships such a file, and writes another at runtime, but on nixpkgs **neither matches**: `bin/sunshine` is a `makeWrapper` shell script that execs `bin/.sunshine-wrapped` (to set `LD_LIBRARY_PATH` for vulkan-loader), so `/proc/<pid>/exe` is the wrapped binary while both desktop files name `bin/sunshine` — the packaged one directly, the runtime one because the wrapper's `exec -a "$0"` restores that argv[0]. The interface is therefore denied, and the failure is silent and looks exactly like a hang: Sunshine logs `Found output: Virtual-0`, then blocks forever waiting on frames that never arrive and never binds its ports. This was observed on the first live activation, not reasoned about in advance. The module closes the gap by installing one more desktop file requesting the interface for `bin/.sunshine-wrapped`, which is the path that actually connects; with it, Sunshine reaches `Screencasting with KWin ScreenCast`, creates its PipeWire stream and comes up normally.

`capSysAdmin` must stay `false` for the same reason: it would repoint `ExecStart` at `/run/wrappers/bin/sunshine`, changing `/proc/<pid>/exe` again and invalidating the desktop file above. `cap_sys_admin` is a KMS capture requirement and buys nothing here. `KWIN_WAYLAND_NO_PERMISSION_CHECKS=1` is the blunt escape hatch if the match ever breaks again, at the cost of disabling the check for every client.

`streamer` holds `uinput`, `render` and `video`, and deliberately not `input`. Sunshine's own documentation says to add its user to `input`, which grants read on every `/dev/input/*` — on a machine somebody types at all day, that is a keylogger sitting in an unattended service that runs 24/7. Sunshine only needs to *create* virtual devices, which is `/dev/uinput` alone, and `hardware.uinput.enable` (set by the Sunshine module itself) provides exactly that group. `audio` is withheld for a related reason: with no access to real hardware, this user's PipeWire graph has no sinks at all, so a declared null sink becomes the only sink, therefore the default, therefore what Sunshine captures — and stream audio can never be routed to the desk's speakers by accident. The isolation is structural rather than configured.

Two smaller calls. Sunshine is overridden with `cudaSupport = true` because the nixpkgs default is `false` and Turing's NVENC path in Sunshine is the CUDA-backed one; the alternatives are nvidia's weak VAAPI encode shim or software x264, neither of which is a real answer on a 2080. This costs a long local build that the binary cache will not have, repeated on nixpkgs bumps. And no codec list is pinned: Turing advertises H.264 and HEVC and never offers AV1 (encode starts at Ada), so negotiation already produces the right answer, and a pinned list would just be a lie waiting to break on a GPU swap.

The virtual output is a single fixed 1920×1080. `--virtual` sets geometry at process start with no runtime mode switching, and Sunshine's `output_name` is global with no per-app override, so a second output could never be selected per app entry regardless. Handheld 720p is served by letting Moonlight request it and Sunshine scale, which wastes some GPU rendering a 1080p frame nobody sees at full size. Retuning the output per app entry via a `kscreen-doctor` `prep-cmd` — the pattern the nixpkgs Sunshine module's own example uses — is the upgrade path if KWin's virtual backend turns out to expose settable modes; the output is named `Virtual-0`.

The two things that could have invalidated this design were checked against a real `kwin_wayland --virtual` on this hardware before the module was trusted. The virtual framebuffer is rendered on the NVIDIA GPU rather than the CPU — the failure mode that would have killed the whole approach — which `qdbus org.kde.KWin /KWin supportInformation` reports directly as `Compositing Type: OpenGL`. That D-Bus reading is the only valid check. Presence of `zwp_linux_dmabuf_v1` in the globals list was used as a proxy for it at first and is **not** one: a KWin confirmed on OpenGL does not necessarily advertise it to an ordinary client, and every conclusion drawn from that proxy while chasing the QPainter-at-boot bug turned out to be noise. It presents exactly one output, `Virtual-0`, at 1920x1080@60 with a physical size of -1mm, i.e. a framebuffer no monitor could claim. `zkde_screencast_unstable_v1` is deliberately absent from an ordinary client's global list: it sits in KWin's `interfacesBlackList` and is only handed to a client whose executable path matches a desktop file requesting it, which is precisely the mechanism Sunshine's shipped `.desktop` file exists to satisfy.

Input needs a bridge, and that is a consequence of the virtual backend rather than an oversight in configuration. Sunshine injects input only through uinput (inputtino): it creates real kernel input devices, which requires some compositor to read them back through libinput. KWin's `setupInputBackends()` asks the output backend for an input backend and then unconditionally adds a `FakeInputBackend`; `createInputBackend()` is overridden only by the drm, wayland and x11 backends, so `VirtualBackend` returns nothing and a `--virtual` session has no libinput at all. Sunshine's devices therefore have no reader, and mouse, keyboard and gamepad are all equally dead — the symptom is not partial. The alternatives were a wlroots headless compositor with `seatd` (which works, but drops Plasma and would have the session reading real input devices unless scoped by udev) or `org_kde_kwin_fake_input`, the one input path a virtual session does have. The latter was chosen, which costs a small bridge daemon (`packages/kwin-uinput-bridge`) that reads the `Sunshine *` evdev nodes and replays them as fake_input requests.

Two details of that bridge matter. It is installed **unwrapped**, because it must satisfy the same `/proc/<pid>/exe` match against its desktop file that Sunshine's wrapped binary fails; a `makeWrapper` shim would silently break input the same way it broke capture. And access to the devices comes from a udev rule matching `ATTRS{name}=="Sunshine*"` and handing them to the `uinput` group, rather than from putting `streamer` in `input`. That is strictly narrower than what Sunshine's documentation asks for: the session can read the virtual devices it is meant to replay and provably nothing else on the machine, so the keylogging exposure that made `input` unacceptable never arises. The devices must also be hidden from the *desk*. They are real kernel input devices, so Hyprland — which runs on a real seat and reads `/dev/input` through libinput — opens them like any other mouse and keyboard, and remote input drives both sessions simultaneously: moving the mouse in Moonlight moves the cursor on the physical monitors. Permissions are not the lever here, because libinput obtains devices through logind rather than by group. The fix is `ENV{LIBINPUT_IGNORE_DEVICE}="1"` on the same udev rules: libinput skips the device outright, while the bridge is unaffected because it opens the evdev node directly rather than through libinput, and KWin needs no exemption because the `--virtual` backend has no libinput at all. One residue remains: a program on the desk that reads evdev directly rather than through libinput — Steam among them — can still see the virtual *gamepad*, since no udev property hides a device from raw evdev.

Gamepads are deliberately excluded from the bridge — games open evdev directly, so they need the udev rule and nothing more, and fake_input has no gamepad concept anyway.

The session units source `/etc/set-environment`, and that is load-bearing twice over. A lingering user never runs pam_systemd or a login shell, so its systemd manager carries only systemd's minimal default environment; `startplasma-wayland` sets `XDG_CONFIG_DIRS` but merely inherits `XDG_DATA_DIRS`, and NixOS gives user units a `PATH` of coreutils, findutils, grep, sed and systemd alone. Unset `XDG_DATA_DIRS` makes KService fall back to `/usr/local/share:/usr/share`, so every desktop file under `/run/current-system/sw/share` is invisible — including the screencast permission file above. The `PATH` gap is worse, because it fails silently and at a distance: KWin spawns `Xwayland` by bare name, and with `--xwayland` the wrapper creates the X11 listening socket up front while starting Xwayland lazily on first client connection. An unfindable Xwayland therefore produces no error at all — the socket simply exists and never accepts, and any X client blocks in `connect()` indefinitely. Sunshine's `input::init()` is such a client, so the whole thing presented as Sunshine hanging with no log output after `Found output: Virtual-0`, several layers away from the actual cause. Confirmed by A/B: an otherwise identical `kwin_wayland --virtual --xwayland` spawns Xwayland on first connect when the environment is sourced, and never spawns it when it is not.

One operational consequence of running the session under a lingering user: `nixos-rebuild switch` restarts system units and the units of the user performing the switch, but it does not touch another user's systemd manager. The Stream Session therefore keeps running the previous closure after a rebuild, which presents as a config change that appears to have applied but changed nothing — the symptom that first surfaced the capture-authorisation bug above. Applying a change to this module means `sudo systemctl restart user@$(id -u streamer).service`, or a reboot. Wiring that restart into activation automatically is possible via a oneshot with `restartTriggers`, and was left out deliberately: it would kill an in-progress stream on any unrelated nixpkgs bump that touches the Sunshine closure.

Lingering also puts the session in a race it loses. `user@1001.service` starts at the very beginning of boot, and on cleoDesktop KWin reached its compositor selection 2.1 seconds *before* the kernel finished registering `/dev/dri/renderD128` — `nvidia-drm` initialised at 01:13:55.897 against KWin's `Configured compositor not supported by Platform. Falling back to defaults` at 01:13:53.799. `VirtualBackend` offers OpenGL only when it can open a DRM render node, so with none present the session came up on QPainter, KDE screencast refused it, every Sunshine encoder probe failed and Moonlight showed a bare 401. `stream-session-start` therefore waits for the render node before starting Plasma at all. The ordering belongs in systemd — `After=dev-dri-renderD128.device` — but the user manager has no device units, so a poll is the available seam.

Restarting `stream-session.service` is not a way to restart the compositor, and believing otherwise cost a whole debugging session. `startplasma-wayland` brings the session up by starting systemd user units, which then outlive it; `plasma-kwin_wayland.service` in particular keeps running when `stream-session.service` is killed, and starting the unit again finds KWin already active and does nothing. A self-heal that killed `startplasma-wayland` on a bad compositing type therefore looped without ever replacing the KWin it was complaining about — and, because no new KWin was spawned, logged nothing, which read as KWin being mysteriously silent. Replacing the compositor means `systemctl restart user@1001.service` or a reboot.

Finally, `origin_web_ui_allowed` is left at its default of `lan`. `openFirewall = true` opens Sunshine's ports on every interface including `tailscale0`, so streaming works remotely, but the Web UI and PIN pairing do not: Tailscale's 100.64/10 addresses are not LAN by Sunshine's reckoning. Pairing a new client is therefore a from-home operation. Changing that setting to `wan` would exchange a real security boundary for the convenience of remote pairing, and was not worth it for a household of already-paired devices.
