# Run Hermes Agent In Its Official Docker Image, Not A VM

The Hermes Agent gateway now runs as a docker compose stack from the upstream `nousresearch/hermes-agent` image (`modules/containers/hermes.nix`, `nixosModules.hermesContainer`, reached through `dockerFullStack`). ADR 0001's Debian libvirt VM is deprecated: no host imports `nixosModules.hermesVm`, and the module survives only so `/mnt/raidDrive/vms/hermes` can be drained. This is not a reversal of 0001's requirements — upstream shipped an image that satisfies them, which did not exist when 0001 was written.

Each of the four reasons 0001 gave for a VM is now met without one. **Guest systemd** was wanted for supervision; the image runs s6-overlay v3 as PID 1 and supervises the dashboard and every per-profile gateway with restart backoff, which is the whole of what the VM's systemd was doing. **Hypervisor-enforced memory limits** become the cgroup limits in `deploy.resources.limits`, carried over at the domain XML's own numbers (8G, 4 CPU) — Compose v2 applies these outside swarm, so they are a real ceiling and not the swarm-only no-op they are often mistaken for. **Snapshot/reset** gets cheaper, not worse: `/opt/hermes` is immutable at runtime and every piece of mutable state is one host directory, so a reset is a directory restore and a rollback is an image tag, where before it was a qcow2 backing-file dance. **Its own LAN IP** is the one requirement deliberately dropped — nothing ever addressed `192.168.0.50` directly, caddy always fronted it, and the new stack publishes nothing to the LAN at all. The Debian familiarity argument also survives intact, since the image is built on `debian:13.4`; what it adds over the VM is that Python 3.13, Node 26, Playwright/Chromium, ripgrep and ffmpeg arrive pinned instead of being installed by hand into a guest nothing in this repo described.

**Multi-profile is one container, not a container per profile.** `hermes profile create <name>` registers an s6 service slot at runtime, so profiles are supervised siblings sharing one data dir, one interpreter cache and one dashboard backend on 9119 (the Desktop client sends the target profile with each request). Upstream warns that two gateway processes pointed at the same data directory will corrupt sessions and memories, so isolation between profiles has to come from the s6 slots and *not* from duplicating the stack — a second compose service would be the obvious-looking wrong answer here. The module's `profiles` attrset is therefore not a list of containers: it declares which profiles get their own OpenAI-compatible API server and on which port, and drives three things — the published ports, the `API_SERVER_*` keys written into each profile's `.env` before the container starts, and a `docker exec ... profile create` for any profile whose directory does not exist yet. Creation stays imperative because the s6 slot only exists at runtime; everything a fresh container needs to come up correctly is written by `preStart` on the host, so a port change in Nix is already in the `.env` when that gateway boots.

**API keys are not in sops, and this is deliberate.** They live in `/var/lib/stacks/hermes/.env`, mode 0600 in a 0700 directory owned by the image's fixed uid 10000. ADR 0002's rule is that secrets never reach the git repo or a world-readable nix store, and a file written by `hermes setup` into the data dir breaks neither. Routing them through sops would mean the values must exist in `secrets/secrets.yaml` before the stack can activate at all, to re-render a file the setup wizard writes anyway and that Hermes rewrites as chat platforms are linked. The trade is real and should not be discovered by surprise: this `.env` is the one piece of lunaServer's service configuration that is neither in the repo nor reproducible from it, and it is on the root disk rather than raidDrive, so it needs whatever backup the rest of `/var/lib/stacks` gets.

**Dashboard auth is the carve-out, and it is declarative.** `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`, `_PASSWORD_HASH` and `_SECRET` reach the container through compose's `env_file:`, which is the pattern ADR 0002 already names for every stack here. The argument above does not reach them: the setup wizard does not write them and Hermes does not rewrite them when a chat platform is linked, so there is no file for sops to fight over. Upstream documents container environment as overriding the data dir's `.env` and names secrets-manager integration as the reason it does, so this is the supported direction rather than a trick, and the plaintext exists only in `secrets/secrets.yaml` and on `/run`'s tmpfs. What sops stores is the plaintext password, and it is never what the container receives: `preStart` reads it from `/run/secrets`, derives Hermes' scrypt hash, and writes `/run/hermes/dashboard.env` at 0400. Neither form reaches the store, so rotating the password is `sops set` plus a rebuild rather than a hand-run `hash_password` inside the image.

Hashing at **activation** and not in a derivation is the entire point, and it is not a stylistic choice: a derivation's inputs land world-readable in the nix store, and this repo is public. The scrypt parameters are upstream's — `scrypt$N$r$p$<b64 salt>$<b64 dk>`, n=16384, r=8, p=1, a 16-byte salt and a 32-byte output, no pepper — checked against a hash the image itself produced rather than read off a docs page. Should upstream ever change them the failure mode is a rejected login, which is loud and recoverable, not a silently malformed file. `preStart` also verifies the hash already on disk against the current plaintext and leaves it alone when it still matches: a fresh salt on every rebuild would change the env file, and compose recreates a container whose environment moved, which would kill every running agent session for nothing. `_SECRET` signs dashboard sessions and must be stable for the same reason — without it, every restart logs every session out. The `env_file:` entry uses `format: raw`, which is not decoration: Compose interpolates unquoted env-file values, and a scrypt hash is `scrypt$N$r$p$salt$hash`, so `$salt` parses as a variable reference and expands to nothing. The corruption is silent in the worst way — the provider still registers on a non-empty value, so the dashboard comes up and serves a login page that rejects the correct password.

One upstream trap belongs in the record because the error message does not name it: `hermes setup` writes `basic` into `plugins.disabled` in the data dir's `config.yaml`, and the dashboard then still refuses to bind with "no auth providers are registered" however correct the credentials are ([NousResearch/hermes-agent#54489](https://github.com/NousResearch/hermes-agent/issues/54489), v0.17.0). `config.yaml` is the wizard's file and is not managed from here, so the fix is manual and one-time: move `basic` out of `plugins.disabled` into `plugins.enabled`.

**The Obsidian vault is bind-mounted read-write, and reached by ACL rather than by group.** `/mnt/raidDrive/isaac/Obsidian` appears in the container at `/mnt/isaac/Obsidian` — the path every client already has over NFS — so a note or skill that names the vault resolves the same on the agent as on a desktop. The image's fixed uid 10000 is not isaac and is not in `users`, so it needs a grant. `group_add` with the `users` gid would have worked and was rejected: it would have required making `/mnt/raidDrive/isaac` group-traversable, which hands the container the whole of isaac's private directory to reach one subtree of it. The tmpfiles ACL rules instead give uid 10000 `--x` on `/mnt/raidDrive/isaac` (traverse, without the right to list it) and `rwx` on the vault, plus a default ACL so notes the agent creates inherit the grant. Neither rule recurses, so files that predate them need a one-off `setfacl -R -m u:10000:rwX /mnt/raidDrive/isaac/Obsidian` and `setfacl -R -d -m u:10000:rwx` on the same path. xfs carries ACLs without a mount option, so nothing in the fstab changes.

Read-write is a deliberate choice and worth stating next to the sandbox note below: this is an agent with shell tools, so it can rewrite or delete any note in the vault, not only the ones it authored. What protects the vault is Syncthing's versioning and whatever backup `/mnt/raidDrive` has — not this mount.

Two exposure decisions differ from the VM and from the other stacks here. Every port is published to `127.0.0.1` only, not to the LAN: an unset `API_SERVER_KEY` leaves the OpenAI-compatible endpoint unauthenticated, and that endpoint drives an agent with shell and browser tools, so it is loopback-only until a profile has a key and someone adds a caddy vhost on purpose. `hermes.luna.local` keeps working and now proxies the dashboard, which is why its basic auth is sops-declared rather than optional — it supervises every profile and the LAN can reach it through caddy. The dashboard binds `0.0.0.0` inside the container because a container-loopback bind is unreachable through a published port, and a non-loopback bind engages Hermes' auth gate, so an unauthenticated dashboard is not a state this stack can boot into. Upstream is equally plain that the username/password provider is for a trusted LAN or a VPN and not for direct public-internet exposure; anything WAN-facing needs the OAuth provider instead. The cost of the whole move, stated plainly: the hypervisor boundary is gone. An agent that runs arbitrary shell and browser tools now shares lunaServer's kernel, confined to uid 10000 in a container. For that reason `/var/run/docker.sock` is **not** bind-mounted even though the image ships `docker-cli` and would use it — that mount is root on the host, and it would hand the agent the machine.
