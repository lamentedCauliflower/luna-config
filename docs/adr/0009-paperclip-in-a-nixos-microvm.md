# Run Paperclip In A NixOS MicroVM, Not Its Docker Image

Paperclip and every agent it runs now live in a NixOS guest on lunaServer, declared with microvm.nix (`modules/features/paperclip-vm.nix`, `nixosModules.paperclipVm`). The docker compose stack it replaces (`ghcr.io/paperclipai/paperclip` plus a rootless `docker:dind-rootless` sidecar) is gone. Paperclip's agents are CLI subprocesses of the server, so whatever machine runs the server is the agents' dev environment. The Debian image gave them no compiler, no nix and no docker client, and each tool had to be bind-mounted into it as a static binary. The guest gives them `nix shell`, per-project devenv and an ordinary docker daemon.

**A VM, not a NixOS container.** A NixOS container (systemd-nspawn) shares the host's nix daemon. Agents would then have to stay untrusted users of luna's daemon, because a trusted user there is root on luna, which makes devenv's cachix and `--option` calls awkward. Worse, fixed-output builds run in luna's network namespace, outside the egress rules, so an agent could reach the LAN through a build. Docker inside an nspawn container with its own user namespace is also painful. In the VM the guest runs its own daemon, agents are its trusted users, and docker is just `virtualisation.docker`. The rootless dind sidecar, its renamed passwd, the subuid range, the pinned-uid workarounds and the entrypoint chown hack all went away with the image.

**Paperclip is the upstream image's `/app`, not an npm install.** Before each VM start, luna's docker copies `/app` out of `ghcr.io/paperclipai/paperclip`, pinned by tag and digest, into `/paperclip/.app`. It does nothing when the pinned image is already there. The guest symlinks that copy to `/app`, because the runtime bundle hardcodes paths under it, and runs the image's own `node server/dist-runtime/index.mjs` with the image's env. `programs.nix-ld` runs the prebuilt glibc binaries inside it: embedded Postgres, the runner, and the Claude Code bundled with the agent SDK. Upgrading means bumping tag and digest, rather than docker-auto-update pulling `:latest`.

The first cut installed `@paperclipai/server` from npm, and that was wrong. The image's dependency tree comes from a pnpm lockfile with Paperclip's own patches (`claude-agent-acp` agent isolation and allowed tools, `acpx`, `embedded-postgres`, `postgres`) and version overrides. npm applies none of them. The visible failure was ACP runs reaching an unpinned SDK whose bundled Claude Code (2.1.257) the API rejected for current models; the silent one was running agents without upstream's isolation patch. Packaging it as a derivation was rejected too: it is a pnpm monorepo plus a Rust runner plus downloaded assets, released daily, and embedded Postgres writes into its own package at start.

**State did not move.** `/var/lib/stacks/paperclip` is a virtiofs share mounted at `/paperclip`. Paperclip's database stores absolute paths under `/paperclip`, the share passes the docker-era uid 987 through, and the snapshot before each start runs on the host exactly as before. The guest's own closure boots from a store image rather than a share of the host's `/nix/store`, so agents never see the host store. Agent builds go to a writable overlay on a volume. Its nix database is on the tmpfs root, so overlay paths are fetched again after each VM restart; that is a known cost, marked in the module.

**The database's container-era paths are kept valid, not edited.** The Local environment's env vars, the `gitea` Tools connection and an encrypted company secret name `/usr/local/bin`, `tcp://dind:2375`, `/run/user/987/docker.sock`, `http://10.200.0.1:3000` and `/run/secrets/gitea-token`. The guest symlinks `/usr/local/bin` to the system profile, resolves `dind` to loopback with dockerd also listening there, and installs the gitea token at the same path. It also uses the old bridge's subnet for SLiRP, so luna is still `10.200.0.1`. That is why cutover needs no database change. Once the env vars are rewritten for NixOS through the board, the shims can go.

**Networking is SLiRP, and the egress sandbox moved to the qemu uid.** With user-mode networking every guest connection, including docker test containers, is a socket of the qemu process on luna. One `OUTPUT` rule on the `microvm` uid therefore enforces what the old `br-paperclip` mangle chain did: the internet is open, and luna, the LAN, other stacks and the tailnet are refused, except Gitea's web port. caddy still proxies `127.0.0.1:3100`, now a SLiRP port forward. The guest resolves through 1.1.1.1, because SLiRP would forward to luna's tailscale resolver, which the rule blocks. SLiRP's throughput is far below a tap with vhost-net. That was accepted for an API-bound workload, and a tap is the upgrade if it ever matters.

Secrets stay in sops on the host and reach the guest as systemd credentials through qemu's fw_cfg (`microvm.credentialFiles`), so they never enter the guest's store image. The cost of the move: the VM's 12 GiB is a ceiling backed by balloon free-page reporting rather than a hard reservation, and luna has 23.5 GiB.
